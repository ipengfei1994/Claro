# 作品集案例：Claro — 内容安全治理平台

> 一个从"检测模型"长成"可追溯治理系统"的项目。本文只写真实发生的事：真实的问题、真实的取舍、真实的数字。

---

## 1. 背景与问题

SLG（策略类手游）的社区治理有一个典型困境：玩家之间的冲突不是简单辱骂，而是"导流 + 欺诈 + 骚扰"的复合体，且往往跨频道、跨联盟发生。审核团队面对的不是"要不要封号"，而是：

- 这条消息到底该自动处理，还是该有人看一眼？
- 如果封错了，能不能解释清楚当时看到了什么？
- 上个月定的策略，这个月还合适吗？

现有工具大多停在"关键词命中 → 打标签"。但标签不产生决策，决策才需要被解释、被复核、被回溯。Claro 的出发点就是这句话：**治理的重点不是判定，而是判定的可追溯性。**

## 2. 目标与硬约束

我把项目约束写死，因为约束决定了取舍：

| 约束 | 为什么 |
|---|---|
| 只跑 Windows 11 原生，不用 Docker / WSL | 想验证这套系统在没有容器编排的单机环境里能否被完整复现与操作 |
| 不用 MySQL | PostgreSQL 的 JSONB、部分索引、`FILTER` 聚合是设计的一部分 |
| 不推翻前五个阶段的架构 | 产品化不是重写；能修就修，能补就补 |
| 不伪造测试与性能数据 | 一旦开始编数字，整个项目的可信度归零 |
| 不做"静态页面假装有功能" | 界面上每个数字都必须来自真实查询 |

这些约束后来救了我很多次——每当想"要不要临时 mock 一下"，答案已经被写死了。

## 3. 方案与关键取舍

### 取舍一：为什么要做统一入口，而不是再加一条流水线

到 Phase 05 结束时，系统有 Kafka 消费链路能处理消息，但没有一个"给我一条消息，走完全流程"的入口。做演示、写测试、排查问题都得手工拼五个服务。

我加了 `ClaroProcessingService.process_message()`，但它**不实现任何业务逻辑**，只做编排和状态归集：

```
validate → ingest → detect → publish → governance
```

每个阶段包一层 `_Stage` 上下文管理器，记录状态、耗时、detail。返回值只有四种状态：`processed / duplicate / partial / failed`。

这个决定的代价是多了一层抽象；收益是"单条处理"和"Kafka 消费"从此共用同一套下游逻辑，不会出现两套实现慢慢漂移。

### 取舍二：幂等键为什么要三层

第一版只做了 `event_id` 去重，结果演示脚本重放时报错：`event_id was reused with a different payload`。原因是哈希里包含了 `occurred_at`，重放时时间戳变了。

修正的做法是把哈希改成**内容寻址**——只对 `event_id + event_type + payload` 做哈希，不包含发送时间。但这还不够，因为 Kafka 重投和业务重算会出现在不同层：

| 层 | 幂等键 | 解决的问题 |
|---|---|---|
| 入库 | `(topic, partition, offset)` + `event_id` + 内容哈希 | Kafka 重复投递 |
| 检测 | `risk_result.message_id` 唯一 | 重复检测 |
| 决策 | 确定性 `decision_key` | 重复裁决 |

三层缺一不可。这也是为什么演示脚本可以反复运行——第二次全部返回 `duplicate`。

### 取舍三：宁可显示"不可计算"

分析层最反直觉的决定：分母小于 30 的比率，**不返回值**。

```python
gated_rate(numerator, denominator, threshold=30, label)
# denominator < 30 → value=None, low_sample=True, 保留真实样本量
```

后果是总览页上"自动处置率"长期显示"不可计算 · 样本量 8，不足，已抑制"。看起来像没做完，实际上是刻意的：一个基于 8 条样本的"87.5%"会被当成结论，而它什么都不是。

### 取舍四：主题用框架原生能力，不用 CSS 覆盖

Phase 05 用 CSS 变量覆盖实现深色模式，看起来能用。直到截图检查发现：页面背景变深了，但 `st.dataframe`、输入框、按钮仍是浅色，文字直接看不见。

修法不是继续加 CSS，而是删掉覆盖，改用 Streamlit 原生的 `[theme.light]` / `[theme.dark]` 配置。代价是所有自定义颜色要重新按主题取值；收益是**每一个**内置组件都自动正确。

顺带发现一个连带问题：`src/claro/ui/pages/` 这个目录名会让 Streamlit 把它识别成多页应用，和显式导航打架。于是重命名为 `screens/`，并在 `__init__.py` 里写清楚原因，避免下一个人再踩。

## 4. 实现难点

### 难点一：语义等价的 SQL 重写，性能差 4 倍

总览页要统计"每天的高风险消息数"。第一版用 `LEFT JOIN LATERAL (array_agg(severity ORDER BY ...))` 取每条消息的最高等级。逻辑正确，但每行都执行一次 array_agg：

```
daily_timeline   255.6 ms   →   64.0 ms   （分组 CTE + 连接，4.0×）
dataset_summary  201.0 ms   →   36.3 ms   （相关子查询 → LEFT JOIN 聚合，5.5×）
server_risk      191.2 ms   →  138.3 ms   （同 daily_timeline 手法，1.4×）
```

关键是**先测再改**：我先记录每个查询的独立耗时和 `EXPLAIN ANALYZE` 计划，改完再测一遍，只保留真的更快的那一版。没有做"顺手加索引"这种没有证据的优化。

### 难点二：`pandas.Timestamp` 不是 `datetime`

`fmt_relative()` 对所有时间做 `astimezone()` 转本地时区。单元里传字符串没问题，从 DataFrame 里取出来就崩：

```
tz_convert() takes exactly 2 positional arguments (1 given)
```

因为 `pandas.Timestamp` 虽然是 `datetime` 子类，却重写了 `astimezone` 且不接受无参调用。修法是先 `to_pydatetime()` 再转换，并把整个函数包在 try/except 里对 `NaT` 兜底。

这类 bug 的价值在于：它只在真实数据流里出现，单测和类型检查都抓不到。

### 难点三：审核动作的语义陷阱

演示脚本想用 `reject` 触发拦截，一直失败。读了状态机才发现：`reject` 的语义是"认为不该处置"，所以解析成 `allow`。

这不是 bug，是设计。想拦截必须显式 `override`，并同时给出 `final_action` 和 `final_level`。我把演示流程改成 `override → mute`，并在文档里把这个语义写清楚——**不允许用否定的名义做肯定的事**，这条规则值得留下来。

### 难点四：Windows PowerShell 的两个坑

1. `Start-Process` 报 `已添加项。字典中的关键字:"HTTPS_PROXY"`：PS 5.1 把进程环境块（大小写不敏感）拷进 .NET 字典（大小写敏感），`HTTPS_PROXY` 与 `https_proxy` 并存就炸。修法是在脚本加载时把所有大写重复项归一化。
2. Kafka 起不来报 `系统找不到指定的文件`：JDK 路径解析函数返回了 `<jdk>\bin`，调用方又拼了一次 `bin\java.exe`，变成 `bin\bin\java.exe`。修法是归一化到 JDK 根目录并显式检查 `Test-Path`。

这两个都是"在干净 shell 里才会暴露"的问题——开发时手工起过服务，脚本路径从没被真正走过。

## 5. 结果

| 项 | 结果 | 怎么验证的 |
|---|---|---|
| 数据规模 | 50,018 条消息、8,856 风险事件、8,897 原子证据 | SQL 直接查 |
| 单条流水线 | p50 81–103 ms，p99 134–268 ms（1k/10k/50k） | 每档 200 样本实测 |
| 批量入库 | 64–94 行/秒 | 全量计时 |
| 总览读模型 | 2.4 s（16 次查询） | 干净库重复测量 |
| Redis 缓存 | 命中率 98%，4.5 ms/次 | `INFO stats` 差值 |
| 页面渲染 | 15 个页面，0 异常 | AppTest + 真实浏览器双验证 |
| 幂等 | 演示脚本重复执行全部 `duplicate` | 连跑两次比对 |

一致性验证：三条独立路径重算同一指标结果一致；回放前后 9 张业务表内容级 SHA-256 指纹不变。

## 6. 反思

**做得对的**

- 先审计再动手。Phase 06 第一步不是写代码，而是产出一份 11 个 P1 缺陷的清单，按 P0/P1 排序。修 JDK 路径和重复环境变量这两件事，如果不先跑"干净 shell 启动"根本发现不了。
- 坚持"数字必须可追溯"。低样本门禁让界面变难看，但每次解释它都比解释一个假指标容易。
- 把"不假装"写进约束。Hive 没装这件事在文档、界面、自检脚本里各出现一次，三处一致。

**做得不够的**

- 批量入库吞吐只有 64–94 行/秒。根因是每条消息一个独立事务。改成批量事务应该有 5–10 倍提升，但这个改动会动到幂等边界，我选择记录下来而不是在收尾阶段冒险。
- 总览 2.4 秒仍然偏慢。16 次查询每次独立开连接，连接复用和查询合并都还没做。
- 没有 CI。Windows 原生依赖太重，本地 `run_tests.ps1` 是唯一入口。

## 7. 如果重做

1. **数据模型先行，界面后置**。这次是界面倒逼我去想"这个指标到底该怎么算"，虽然有收获，但顺序反了。
2. **性能基准放在 Phase 02 而不是 Phase 06**。批量入库的瓶颈如果在数据层刚写完时就测出来，改动成本会低得多。
3. **幂等键一开始就按"内容寻址"设计**。包含时间戳的哈希是个典型错误，代价是排查了一整轮演示失败。
4. **UI 主题不要自己造**。框架提供的原生能力通常比手写覆盖更完整，尤其在"内置组件是否跟随主题"这种细节上。
